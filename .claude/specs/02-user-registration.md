# User Registration - Specification

## Overview
Add a "Register" menu item to the frontend header. Clicking it opens a modal containing a form that mirrors the `User` model (username, email, password). On submit, the form posts to a new backend endpoint that creates the user in MongoDB. On success the modal closes and the landing page (ExpenseSummary and ExpenseList) re-fetches and re-renders so the new user appears.

## Scope
- Affects: both
- Priority: Medium
- Estimated Effort: medium

## Requirements

### Functional Requirements
1. The header navigation shows a new "Register" item (button styled as a `nav-link`, not a page-navigating anchor).
2. Clicking "Register" opens a modal dialog with fields: `username`, `email`, `password`. The `uid` field is **not** shown; it is generated by the backend.
3. Client-side validation before submit:
   - username: required, trimmed, 3-30 chars
   - email: required, valid email format
   - password: required, minimum 8 chars
4. Submit calls `POST /api/users` through a new `registerUser()` function in `services/expenseService.ts` (no direct `fetch()` in components).
5. While the request is in flight, the submit button is disabled and shows a loading state.
6. On `201 Created`: close the modal, reset the form, show a success toast, and trigger a re-render/re-fetch of the landing page data (summary + expense list).
7. On error (`400` validation, `409` duplicate username/email, `500`): keep the modal open, keep the entered values (except password may be cleared), and show the server's error message inline.
8. The modal can be dismissed via Cancel button, close icon, or Esc without submitting; dismissing resets the form and errors.
9. Backend `POST /api/users` validates input, rejects duplicates, assigns the next `uid`, hashes the password, persists the user, and returns the created user **without** the password.

### Non-Functional Requirements
1. Security: passwords must never be stored in plain text (hash with bcrypt, cost >= 10) and never returned in any API response.
2. Security: server-side validation is authoritative; client validation is only for UX. Trim and lowercase email server-side (the schema already lowercases).
3. Security: error messages for duplicates should not leak more than "username/email already in use".
4. Scalability: `uid` generation must be safe against concurrent registrations (rely on the unique index on `uid`; retry once on a duplicate-key error for `uid`, or use an atomic counter).
5. Accessibility: modal traps focus, is labelled, and form fields have associated labels and error text.

## Design

### Architecture
```
Header (Register button) --onRegisterClick--> App (state: registerOpen, refreshKey)
App renders <RegisterUserModal visible onHide onRegistered />
RegisterUserModal -> registerUser() [expenseService.ts] -> POST /api/users
   -> routes/expenseRoutes.js -> controller.createUser -> User model -> MongoDB
On success: App increments refreshKey -> ExpenseSummary & ExpenseList re-fetch
```

Re-render strategy: `App` holds a `refreshKey` number. It is passed to `ExpenseSummary` and `ExpenseList`, which include it in their data-fetching `useEffect` dependency array (alternatively pass as React `key` to force remount). The existing components currently fetch on mount only, so this is a small change to each.

### Data Model
Backend: no schema change. Existing `User` model is used:
```
{ uid: Number (unique, required), username: String (unique), email: String (unique, lowercase), password: String, timestamps }
```
- `uid` = `(max existing uid) + 1` (or 1 if none).
- `password` stores the bcrypt hash.

Frontend state:
- `App`: `registerOpen: boolean`, `refreshKey: number`
- `RegisterUserModal`: `form {username, email, password}`, `errors`, `submitting`, `serverError`

New TypeScript interfaces in `expenseService.ts`:
```ts
export interface NewUser { username: string; email: string; password: string; }
export interface RegisteredUser { uid: number; username: string; email: string; }
```

### API Endpoints (backend)
```
POST /api/users
  Body: { username, email, password }
  201: { uid, username, email, createdAt }
  400: { error: "<validation message>" }
  409: { error: "Username or email already in use" }
  500: { error: "Internal server error" }
```
Existing `GET /api/users` (returns array of usernames) is unchanged. Note that `getSummary()` builds from all users, so the new user appears in the summary with zeros.

### Components (frontend)
- `RegisterUserModal.tsx` (new) - PrimeReact `Dialog` with form, validation, submit handling
- `RegisterUserModal.css` (new, if custom styling needed)
- `Header.tsx` (modified) - accept `onRegisterClick` prop, add Register button
- `App.tsx` (modified) - own modal visibility and `refreshKey`
- `ExpenseSummary.tsx`, `ExpenseList.tsx` (modified) - accept `refreshKey` prop and refetch on change

### File Structure
```
backend/
  controllers/expenseController.js   (modify: add createUser)
  routes/expenseRoutes.js            (modify: router.post('/users', controller.createUser))
  package.json                       (modify: add bcryptjs)
frontend/src/
  components/RegisterUserModal.tsx   (new)
  components/RegisterUserModal.css   (new, optional)
  components/Header.tsx              (modify)
  components/ExpenseSummary.tsx      (modify)
  components/ExpenseList.tsx         (modify)
  services/expenseService.ts         (modify: registerUser + interfaces)
  App.tsx                            (modify)
```
Existing seed scripts store passwords in whatever form they currently do; they do not need to change for this feature (see Notes).

## Implementation Steps

1. Backend: install `bcryptjs`; add `createUser` to `expenseController.js` (validate, check duplicates, compute `uid`, hash password, save, return sanitized user, map Mongo duplicate-key error `11000` to 409).
2. Backend: register `router.post('/users', controller.createUser)` in `expenseRoutes.js`; confirm `express.json()` is already mounted in `server.js`.
3. Frontend service: add `NewUser`/`RegisteredUser` interfaces and `registerUser()` in `expenseService.ts` (POST JSON, throw an Error carrying the server `error` message on non-2xx).
4. Frontend: build `RegisterUserModal.tsx` with PrimeReact `Dialog`, `InputText`, `Password`, `Button`; wire validation and submit.
5. Frontend: update `Header.tsx` with the Register button and `onRegisterClick` prop.
6. Frontend: update `App.tsx` with `registerOpen` / `refreshKey` state; render the modal; on success close it and bump `refreshKey`.
7. Frontend: make `ExpenseSummary` and `ExpenseList` refetch when `refreshKey` changes.
8. Manual end-to-end verification (see Testing), then update `CLAUDE.md` (new endpoint, new component, `registerUser()`).

## Testing

### Test Cases
1. Click Register: modal opens with empty username/email/password fields.
2. Submit valid data: `201`, modal closes, toast shown, new user appears in the summary panel with `paid 0 / owes 0 / balance 0`.
3. New document in MongoDB has an auto-assigned `uid`, lowercase email, and a hashed (not plain) password.
4. Submit with empty fields or invalid email or short password: inline errors, no request sent.
5. Submit an existing username: `409`, error shown in modal, modal stays open.
6. Submit an existing email with different casing (e.g. `A@X.com`): `409`.
7. Cancel / Esc / close icon: modal closes and form is reset on next open.
8. `POST /api/users` response and `GET /api/users` never contain the password or hash.
9. Backend down: network error message shown, submit button re-enabled.

### Edge Cases
- Double-click on submit (guard with `submitting`).
- Whitespace-only or leading/trailing whitespace in username/email.
- Two simultaneous registrations racing on `uid`.
- Empty `users` collection (first `uid` = 1).
- Extremely long inputs (enforce max lengths server-side).
- Extra/unknown fields in the request body (e.g. client-supplied `uid`) must be ignored.
- Landing page refetch fails after a successful registration (show existing error handling, do not reopen modal).

## Risks & Mitigation

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Plain-text passwords (existing seed data and old model usage) | High | Hash on create; flag existing seed data as a follow-up. No login exists yet, so no compatibility issue. |
| `uid` race condition on concurrent signups | Medium | Unique index on `uid` + retry on duplicate-key error, or atomic counter collection. |
| No authentication/rate limiting on a public create endpoint | Medium | Add basic rate limiting later; out of scope here but noted. |
| Landing components only fetch on mount, so refresh may not trigger | Medium | Explicit `refreshKey` dependency; verified by test case 2. |
| PrimeReact not installed or themed | Low | Check dependencies in step 4; add package and theme CSS if missing. |

## Success Criteria

- ✅ A "Register" item in the header opens a modal with username, email, password fields.
- ✅ Valid submission creates a user in MongoDB via `POST /api/users` and returns `201` without the password.
- ✅ Passwords are stored hashed.
- ✅ Duplicate username/email returns `409` and the error is displayed in the modal.
- ✅ After success the modal closes and the landing page re-fetches, showing the new user in the summary.
- ✅ All frontend API calls go through `expenseService.ts`.
- ✅ `CLAUDE.md` updated with the new endpoint and components.

## Notes

- The original request said the modal should be "equivalent to User model". `uid` is intentionally excluded from the form because it is system-generated; confirm this is the desired behavior.
- The existing `Expense` interface in `expenseService.ts` uses `id: number` while the backend returns Mongo ObjectIds; unrelated to this feature, but worth cleaning up separately.
- Header nav currently uses plain `<a href>` links; the Register item should be a `<button>` styled like `nav-link` to avoid page navigation.
- Login/authentication is out of scope for this spec.
